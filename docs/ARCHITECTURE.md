# V1.0 实现计划与架构

## 实施顺序

1. 固定数据原则：收藏与原生关注独立、字符串 ID、未知父论坛不猜测、写入确认、手动资料库隔离。
2. 完成纯数据层：校验、操作日志归并、删除语义、搜索排序、导入导出与版本边界。
3. 完成 Discord 适配层：SPA 观察、可见语义识别、明确进入来源关联、有限的关注确认。
4. 完成隔离面板：资料库选择、列表管理、设置、对话框、主题、布局与恢复入口。
5. 运行数据、页面边界与应用行为测试；构建单文件，并分别记录模拟覆盖、静态检查与未执行的实机验收。

此五步已在当前实现中完成。发布前的真实 Discord/Tampermonkey 验收仍待执行，不能由单元测试替代。

## 模块

| 文件 | 职责 |
| --- | --- |
| `src/core.js` | 类型与版本校验、字符串 ID、持久存储封装、操作归并、搜索排序、备份和布局约束 |
| `src/discord.js` | 可见 DOM 识别、导航观察、明确的父论坛来源、关注按钮状态确认 |
| `src/style.js` | Shadow DOM 内的面板、长标题、密度、对话框、八方向缩放区域样式 |
| `src/app.js` | 资料库选择、列表操作、设置与焦点、拖动缩放、主题、通知和定期同步 |
| `src/main.js` | Tampermonkey 异步 GM API 适配与启动失败提示 |
| `scripts/build.mjs` | 按明确依赖顺序组合模块，移除模块声明，语法检查并输出独立 IIFE |

生产脚本无全局业务对象、无 `eval`、无 HTML 字符串注入；用户文本使用 `textContent`，链接由校验后的 ID 重建。测试夹具故意暴露应用对象，生产入口不会暴露。

## 资料库及键空间

使用 `dfa:v1:` 前缀：

| 键 | 内容 |
| --- | --- |
| `profile:<uuid>` | 显式命名的本地资料库，不自动推断账号 |
| `prefs:<profileId>` | 资料库界面偏好，包括各服务器的范围与排序 |
| `op:<profileId>:<operationId>` | 独立、不可变的收藏变更记录 |
| `pulse` | 跨标签页唤醒提示；不是权威索引 |

每次刷新需明确选择资料库；同一页面内账号变化无法可靠识别，因此面板持续提醒切换。没有默认自动合并的匿名资料库。不同 Discord 官方子域共享同一用户脚本的 GM 数据，但仍需显式选择资料库。

## 记录格式

`schemaVersion = 1`。记录包含 `guildId`、`threadId`、`forumId`（可为 null）、`guildName`、`forumName`、`originalTitle`、`customTitle`、规范 `url`、`savedAt`、`modifiedAt`、`lastObservedAt`、`source`、`starred`、`nativeFollowState`。

- 所有 ID 必须为字符串。`guildId:threadId` 是唯一身份。
- `customTitle = null` 代表使用完整原始标题，空白重命名会被拒绝。
- `savedAt` 为首次保存时间；`modifiedAt` 为本地变更时间；`lastObservedAt` 为最后一次有字段变化的可见观察时间。没有远端最后回复时间字段。
- `nativeFollowState` 只记录 `unknown` 或曾明确看到 `following`，不代表当前实时关注状态。
- `originalTitle` 不破坏性截断。UI 行数与数据库内容无关。

后续标签、备注、历史或远端观察字段可以通过 schema 升级添加。当前不存在旧版本数据，故不虚构迁移来源。未知版本备份/日志明确拒绝或隔离，不自动清理。未来版本应先读取并验证旧日志，再写入新前缀，保留旧键作为回退，不能原地破坏性升级。

## 变更模型与保证边界

每个操作有随机 UUID、`[毫秒逻辑时钟, 同毫秒序号, 标签页UUID]`、目标身份、类型与字段。写入前先吸收已知日志，逻辑时钟不回退；相同时间以序号和标签页标识得到确定顺序。

操作按顺序回放：

- `put` 仅在当前身份不存在时创建。重复添加不覆盖已有自定义标题、星标或时间。
- `capture` 用于实验性原生关注捕获；遇到曾被明确删除的身份时不恢复，必须手动重新收藏。
- `patch` 只修改指定字段，记录已删除时不生效。
- `delete` 只移除本地可见记录；变更日志保留。后续的字段观察不能复活记录。
- 用户明确再次 `put` 可以重新收藏。真正并发、互未观察到的重新添加与删除按逻辑时钟总序决定结果。

不同身份的写入使用不同键，互不整库覆盖；不同字段的修改能合并。同一字段并发写入确定性决胜，**不保证墙上时钟意义的“最后操作”获胜**；机器时钟变化与并发网络时序会影响顺序。没有 GM 事务/CAS 能力，不宣称线性一致性。

写入后从 GM 读回校验再修改界面。扩展拒绝写入或读回不符则报错；如果写入成功但读回过程出错，不显示成功，之后刷新可能看到实际已保存记录，重试会去重。`pulse` 写入失败不否认已经读回确认的收藏；5 秒可见页轮询和焦点恢复仍能发现记录。

偏好同标签页串行保存、跨标签页最后写入生效，与收藏日志的合并保证分开。没有自动压缩与 GC；存储错误不触发清库。

## Discord 识别策略

- 500 ms URL 检查覆盖 `pushState`/`replaceState`，配合 `popstate`、`hashchange` 与节流的 DOM 观察；不替换 Discord 原生 History 方法。
- 论坛依据已知父论坛记录、可见论坛语义列表标记或创建帖子控件判断。
- 帖子依据已知记录/明确进入链接、线程侧栏标记、或页头/工具栏中的关注控件判断。消息列表内部的按钮不用于关注捕获。
- 只有在已识别论坛列表内点击的同服帖子链接，才建立瞬时父论坛来源。直接 URL、消息链接、其他频道可见性都不充当父论坛证据。
- 不能证明类型时走手动链接确认；不能证明父论坛时保留待归属。语义标记和少量侧栏类名同样可能变动，此适配尚待实机确认。

原生捕获需要可信用户点击、同路由同帖子同资料库、原控件仍连接、逆向标签稳定 650 ms；8 秒内没信号就放弃。右键菜单和替换后的控件不推断。它验证可见 UI 状态，不能验证 Discord 服务器最终状态，默认关闭且如实标为实验性。

## UI、性能与清理

单一 Shadow Root，面板不更改 Discord 主布局。8 个边框/角落调整区，标题栏移动；相对位置和边缘偏移按视口重算。窗口变小只限制显示，不通过单纯移动改写原宽高。三种显示模式、筛选、排序、列表滚动与独立展开标题保留在对应生命周期内。

可选宽屏抽屉未使用；四边均为纵向面板。标题与操作按钮分行，长无空格字符串允许换行；单次渲染 80 条，可继续加载。500 条数据处理已运行逻辑测试，实际渲染性能未测。

主题读取可用 CSS 变量与 computed styles，监听根节点主题属性并以 2.5 秒间隔补偿。渐变不复刻，必要时纯色降级。卸载生命周期清理计时器、观察器、全局监听和同步监听；浏览器 BFCache 页面保留原实例，恢复后继续同步。
